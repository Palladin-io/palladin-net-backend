3. Stabilny header i zależny od suite payload

Nie cały envelope jest blobem. Pola potrzebne do autoryzacji, CAS, transakcji i routingu pozostają jawne oraz są jednocześnie uwierzytelnione przez AAD.

Stabilny header domenowy

  • ProtocolVersion — format całego protokołu
  • CryptoSuiteId — wybór jednej implementacji
  • Purpose — MemberSecret, GrantPayload, Discovery…
  • Scope — OrganizationId, VaultId, EntryId, opcjonalnie GrantId/AgentId
  • ResourceRevision — optimistic concurrency / rollback resistance
  • KeyVersion — generacja klucza użytego przez payload
  • MemberKeyGeneration — fence po usunięciu Membera

XChaChaVaultPayloadV1

{
  nonce: bytes[24],
  ciphertextAndTag: bytes[plaintext + 16],
  wrappedKey?: {
    recipientScheme: "x25519-v1",
    recipientKeyVersion: uint32,
    recipientFingerprint: bytes[32],
    encapsulatedKey: bounded bytes
  }
}

AAD = CanonicalBinary(
  protocolVersion, suiteId, purpose,
  organizationId, vaultId, entryId,
  optionalGrantId, optionalAgentId,
  resourceRevision, keyVersion,
  memberKeyGeneration
)
Warunek bezpieczeństwa: CryptoSuiteId, purpose, scope, rewizje i key version są częścią AAD lub podpisanego transcriptu. Podmiana któregokolwiek pola musi kończyć się błędem uwierzytelnienia.

4. Pobranie wartości secretu przez Użytkownika

Przykład dla odblokowanego web/mobile. Backend zwraca tylko opaque envelope i owinięte klucze.

Faza A — odblokowanie i VK

Wykonywana lokalnie, klucze pozostają w pamięci klienta.

Rozwiąż profil KDF

Klient odczytuje zapisany KdfProfileId. Nieznany profil jest odrzucany.

Argon2id v1 · salt 16 · output 32
Wyprowadź MK / Account Root

Dokładne bajty UTF-8 hasła są przetwarzane wyłącznie lokalnie.

password → Argon2id → AccountRoot → HKDF(AuthCredential, MK)
Otwórz Member private key

Klient uwierzytelnia zaszyfrowany klucz prywatny użytkownika.

XChaCha20-Poly1305 envelope
Pobierz członkostwo Vault

API zwraca WrappedVK przypisany temu Memberowi.

backend sees ciphertext only
Otwórz VK

Member private key otwiera VK; VK pozostaje tylko w pamięci.

X25519 recipient envelope → VK[32]

Faza B — reveal konkretnego Entry

Sekret jest pobierany leniwie dopiero przy reveal/copy/edit.

Pobierz Entry head i current version

API zwraca VaultEntryKey oraz MemberSecretEnvelope.

no plaintext labels / values
Registry rozwiązuje suite

Klient sprawdza protocol, suite, limity i canonical encoding bez fallbacku.

palladin-vault-xchacha-v1
Otwórz EntryDEK

VK uwierzytelnia wrapper związany z EntryId, key version i generation.

VK + AAD → EntryDEK[32]
Wyprowadź MemberSecretKey

Osobny context zapobiega użyciu tego samego klucza dla MemberIndex.

HKDF-SHA-256(EntryDEK, "member-secret")
Odszyfruj i pokaż

AAD wiąże envelope ze scope i rewizją. Plaintext trafia tylko do pamięci UI.

XChaCha20-Poly1305 open → secret
Wyczyść pamięć

Lock, logout, unmount lub koniec operacji usuwa VK, EntryDEK, subkey i plaintext.

zeroize where runtime permits

5. Pobranie wartości secretu przez Agenta

Agent nigdy nie otrzymuje VK ani EntryDEK. Dostaje wyłącznie świeży, filtrowany GrantPayload i per-grant GrantDEK.

Faza A — discovery i approval

Discovery pozwala wybrać Entry bez ujawniania jego danych backendowi.

Agent uwierzytelnia request

Organization API key wybiera tenant; Ed25519 proof identyfikuje konkretnego Agenta.

HTTPS + API key + Ed25519 canonical request
Otwórz VDK w native boundary

Backend zwraca manifest i AgentWrappedVDK dla X25519 identity Agenta.

X25519 recipient envelope → VDK
Przeszukaj Discovery lokalnie

Agent pobiera zaszyfrowane projekcje i odszyfrowuje je VDK-derived key.

HKDF("agent-discovery") + XChaCha open
Wyślij encrypted reason

Reason jest AEAD-encrypted do Vault Message key i podpisany identity Agenta.

fresh ReasonDEK + X25519 wrap + Ed25519 signature
Member zatwierdza

Odblokowany klient czyta MemberSecret, filtruje pola/methods i tworzy świeży GrantPayload.

fresh GrantDEK · no VK / EntryDEK for Agent
Zapis atomowy

Grant state oraz envelope mają właściwy EntryRevision, GrantKeyVersion i pełny scope.

one backend transaction or rollback

Faza B — delivery i użycie

Plaintext powstaje dopiero wewnątrz natywnej granicy Agenta.

Signed credential request

Runtime wysyła entry, method, timestamp, nonce i Ed25519 signature.

get / exec · replay protected
Backend atomowo wydaje envelope

Sprawdza Agent status, grant, TTL, use count, methods, Entry revision i incrementuje użycie.

authorized response only; otherwise no ciphertext
Registry waliduje suite i AAD

Nieznany profil, stara rewizja lub zmieniony AgentId/GrantId kończy operację.

fail closed before plaintext
Otwórz GrantDEK

X25519 private key jest otwierany tylko w wybranej OS/native security boundary.

Agent recipient private key → GrantDEK[32]
Odszyfruj filtrowany payload

Agent otrzymuje tylko zatwierdzone pola, nigdy MemberSecret ani EntryDEK.

XChaCha20-Poly1305 open → approved secret subset
Użyj i wyczyść

get może zwrócić plaintext; exec przekazuje go tylko subprocessowi, a output dla modelu jest withheld.

bounded memory → zeroize → close session

6. Niezmienne reguły bezpieczeństwa

Te warunki są ważniejsze niż nazwy klas i nie mogą zostać osłabione przez abstrakcję.

Suite jest uwierzytelniona

suiteId, purpose, scope, rewizja i key version zawsze należą do AAD lub podpisu.

Registry jest zamknięty

Brak reflection, pluginów, konfiguracji z requestu, negocjacji i domyślnego fallbacku.

Klucze mają purpose

VK, EntryDEK, GrantDEK, VDK, signing key i recipient key nigdy nie są wymienne.

Jedna trwała kopia

Walidacja używa spans/memory; encja wykonuje najwyżej jedną defensywną kopię ciphertextu.

Bounded processing

Rozmiary, batch size i EF tracking są ograniczone; żadna rotacja nie trzyma całego Vaultu w pamięci.

Backend bez plaintextu

Serwer nigdy nie rozwiązuje kluczy ani nie odszyfrowuje envelope. Waliduje strukturę, scope i podpisy.
