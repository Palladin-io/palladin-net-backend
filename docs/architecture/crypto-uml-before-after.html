Na chłopski rozum: kto za co odpowiada

Każdy element ma jedną odpowiedzialność. Identyfikator mówi „który przepis”, registry znajduje przepis, implementacja wykonuje przepis, Value Object nadaje wynikowi znaczenie domenowe, a encja pilnuje procesu biznesowego.

KdfProfileId — numer przepisu na klucz z hasła

To etykieta zapisana przy koncie, np. identity-argon2id-password-v1. Sama niczego nie liczy i nie zawiera hasła.

Kto używa?
Web i mobile podczas rejestracji, unlocku, recovery i zmiany hasła.
Z czego korzysta?
Z lokalnego KdfProfileRegistry, który zwraca implementację Argon2id dla tego ID.
Co daje?
32-bajtowy materiał kluczowy używany dalej do otwarcia zaszyfrowanego private key.
Czego nie robi?
Backend nie wyprowadza MK i nie może podmienić parametrów zapisanych w kodzie profilu.
Account.KdfProfileId→KdfRegistry→Argon2idPasswordV1→AccountRoot

CryptoSuiteId — numer przepisu na envelope

To etykieta zapisana przy ciphertextcie, np. palladin-vault-xchacha-v1. Informuje, jak czytać payload i jakich algorytmów użyć.

Kto używa?
Backend do walidacji struktury oraz web/mobile/Rust do seal/open.
Z czego korzysta?
Z CryptoSuiteRegistry.
Co daje?
Jednoznaczną implementację suite; bez negocjowania parametrów z requestu.
Czego nie robi?
Nie jest kluczem, nie szyfruje i nie przechowuje parametrów w bazie.
Envelope.SuiteId→SuiteRegistry→XChaChaSuite

CryptoSuiteRegistry — zamknięta książka przepisów

To słownik działający w pamięci. Dla znanego ID oddaje dokładnie jedną implementację. Dla nieznanego ID zwraca błąd.

Kto używa?
Contract mapper na backendzie oraz shared crypto layer na każdym kliencie.
Z czego korzysta?
Z bezstanowych implementacji zarejestrowanych w kodzie.
Co przechowuje?
Referencje do implementacji, nie ciphertexty, nie klucze i nie rekordy użytkowników.
Lifetime
Singleton procesu; odtwarzany po każdym uruchomieniu aplikacji.
Registry→Suite v1·Suite v2 w przyszłości

IEnvelopeSuite — umowa dla jednego przepisu

Mówi, jak konkretna suite sprawdza swój własny opaque payload. Nie narzuca wspólnych pól nonce, tag ani wrapper.

Backend
Przekazuje descriptor i blob do ValidateEncodedPayload; suite sprawdza format, canonical encoding i limity.
Klient
IClientEnvelopeSuite dodatkowo szyfruje, odszyfrowuje, sprawdza tag AEAD i wyprowadza subkeys.
Dlaczego?
Nowy format może mieć inny nonce, tag lub wrapper bez zmiany encji domenowych.
Ważne
Backendowe „valid” oznacza poprawną strukturę, nie potwierdzony tag AEAD.

EncryptedEnvelopeContract — paczka przychodząca przez API

To surowe dane z sieci: stabilny descriptor i opaque payload wybranej suite. Traktujemy je jako niezaufane.

Kto tworzy?
Web/mobile podczas zapisu albo Agent podczas encrypted reason.
Kto odbiera?
Backend endpoint i contract mapper.
Co dalej?
Registry wybiera suite, suite waliduje swój blob, fabryka tworzy domenowy Value Object.
Czego nie wolno?
Przekazać contractu bezpośrednio do agregatu lub persistence.
HTTP Contract→Mapper→Suite→Domain VO

EnvelopeDescriptor — etykieta na paczce

To wspólna, stabilna część: mówi, do czego paczka należy i jaką suite trzeba wybrać. Nie opisuje wnętrza ciphertextu.

Co zawiera?
ProtocolVersion, CryptoSuiteId, purpose, scope, revision, key version i opcjonalną key generation.
Kto używa?
Backend do reguł domenowych i wyboru suite; klient jako canonical AAD przy seal/open.
Persistence
Jawne kolumny, aby filtrowanie i kontrola wersji nie wymagały parsowania blobu.
Ważne
Zmiana algorytmu nie zmienia descriptora; zmienia SuiteId i format payloadu.

EncodedSuitePayload — zaplombowana zawartość

To bounded blob, którego wspólna domena celowo nie rozumie. Jego layout należy wyłącznie do suite wskazanej przez CryptoSuiteId.

Suite startowa
Po zdekodowaniu zna m.in. 24-bajtowy nonce oraz ciphertext z 16-bajtowym tagiem XChaCha20-Poly1305.
Przyszła suite
Może mieć zupełnie inne pola i długości bez dodawania ich do wspólnych encji.
Backend
Przechowuje jeden blob i zleca suite wyłącznie strukturalną walidację.
Klient
Wybrana implementacja parsuje blob, wiąże descriptor jako AAD i dopiero z kluczem wykonuje open().

MemberSecretEnvelope — zaszyfrowana wersja Entry dla człowieka

Konkretny Value Object. Łączy opaque ciphertext z dokładnym Vaultem, Entry, rewizją i wersją EntryDEK.

Kto tworzy?
Domenowa fabryka po strukturalnej walidacji suite.
Kto przechowuje?
VaultEntryVersion.
Kto otwiera?
Odblokowany web/mobile posiadający VK i możliwość otwarcia EntryDEK.
Co chroni?
Pełną kanoniczną zawartość Entry i Agent Visibility Policy.

GrantPayloadEnvelope — paczka przygotowana dla jednego Agenta

Zawiera tylko pola i methods zaakceptowane przez Usera. Nie zawiera VK ani EntryDEK.

Kto tworzy?
Odblokowany web/mobile podczas approve lub refreshu.
Kto przechowuje?
Backend jako bieżący payload konkretnego Grant + Entry + Agent.
Kto otwiera?
Native Agent Runtime po autoryzowanym delivery.
Jakim kluczem?
Świeżym GrantDEK owiniętym do Recipient X25519 key Agenta.
MemberSecret→ filtrGrantPayload→GrantDEK→Agent

SignatureSchemeId — numer przepisu na podpis

Oddzielny identyfikator dla podpisów requestów i manifestów. Startowo wskazuje Ed25519.

Kto używa?
Agent runtime do podpisu, backend do verify, User client do podpisów Vault manifest.
Z czego korzysta?
Z zamkniętego SignatureSchemeRegistry.
Dlaczego osobno?
Zmiana podpisu nie powinna wymuszać zmiany szyfrowania każdego Entry.
Co jest podpisane?
Canonical request lub domain-separated manifest/transcript.

RecipientKeyWrapper — koperta na klucz dla odbiorcy

Odpowiada za owinięcie małego DEK do publicznego klucza odbiorcy. Startowo używa X25519 contract.

Kto seal?
User client owija VK/GrantDEK/VDK do wskazanego recipient public key.
Kto open?
User lub Agent posiadający odpowiedni private key.
Backend
Przechowuje wrapper i fingerprint, ale nie może go otworzyć.
Ważne
Recipient fingerprint i wrapper scheme są związane przez AAD/manifest.

Domenowy Value Object — rzecz z konkretnym znaczeniem

To nie interfejs ani encja. Przykład: MemberSecretEnvelope zawsze oznacza MemberSecret, nigdy Grant lub Discovery.

Kto używa?
Agregaty i encje domenowe.
Po co?
Żeby nie pomylić dwóch ciphertextów o podobnym technicznym kształcie.
Stan?
Niemutowalny; prywatny konstruktor i kontrolowana fabryka.
Przykłady
MemberSecretEnvelope, MemberIndexEnvelope, GrantPayloadEnvelope.

Encja / agregat — pilnuje procesu biznesowego

VaultEntry, VaultEntryVersion i GrantEntry nie wybierają algorytmów.

Z czego korzysta?
Z gotowych domenowych Value Objects.
Co sprawdza?
Scope, revision, CAS, lifecycle, key generation i kompletność transakcji.
Czego nie robi?
Nie importuje libsodium/NSec i nie odszyfrowuje danych.
Persistence
EF zapisuje jego stan po zmianie wykonanej metodą domenową.
