# Module: Vault

## Projects
- `Palladin.Module.Vault/` — zero-knowledge vault domain, features, persistence and triggers.
- `Palladin.Module.Vault.Contracts/` — Vault-owned commands and integration events.

## Business responsibility

The Vault module owns tenant-scoped Vault aggregates, structural membership, authenticated encrypted Member projections, key-envelope routing metadata, Entries, grants, and Agent credential delivery. It is a zero-knowledge boundary: Vault display metadata and key material are produced and consumed only by clients.

## Canonical cutover

The service is pre-production and has no data that requires compatibility. `ReplaceVaultWithZeroKnowledgeSchema` therefore resets the existing Vault aggregate graph and replaces the plaintext schema directly. There is no parallel domain model, table family, optional legacy field set, backfill, dual-write, or mixed read path.

The value `protocolVersion = 2` is only the frozen wire/AAD discriminator from the accepted ADR. Palladin is pre-production, so the existing canonical model and schema are replaced directly and incompatible data is reset. It must not be used as a domain/schema suffix: do not introduce `VaultV2`, `VaultV2State`, `EntryV2`, `*V2` tables, duplicate `/v2` endpoints, nullable legacy/new columns, dual reads/writes, backfills or compatibility repositories. Historical “Vault v2” task, contract and document names do not imply runtime versioning. A future protocol negotiation change is distinct from a product/database migration.

## Vault aggregate

`Vault` has the tenant-first primary key `(OrganizationId, Id)` and contains only server-authoritative structure plus opaque authenticated ciphertext:

- structural ownership and timestamps (`IsDefault`, `CreatedBy`, `CreatedAt`, `UpdatedBy`, `UpdatedAt`);
- frozen protocol and algorithm identifiers;
- `MemberVaultMetadata` revision, nonce, key version, and ciphertext;
- typed Member and Discovery sequence counters and retention floors;
- current VK, VDK, Agent message-key, manifest-signing-key, and Member-key generations.

Plaintext `Name`, `Description`, `Icon`, and `Color` columns do not exist. Vault projections are not published to backend Search or Audit. Web and mobile decrypt and match Vault projections locally.

`GET /api/vaults` returns each authorized Member's complete encrypted unlock projection in one bounded page: Member metadata, that Member's wrapped VK, the Discovery-key envelope and both specialized Vault private-key envelopes. Clients can therefore validate and open every listed Vault without an N+1 detail request; the endpoint never exposes raw keys or plaintext presentation data. `GET /api/vaults/{vaultId}` additionally returns the server-owned `metadataRevision` as a canonical unsigned decimal string at the response top level, allowing clients to reject a stale metadata envelope before unwrapping any key material.

`VaultMember` is structural membership only, keyed by `(OrganizationId, VaultId, UserId)`. Wrapped keys are stored separately in `VaultMemberKeyEnvelope`, keyed by `(OrganizationId, VaultId, MemberId, MemberKeyGeneration)`. Rotation adds the committed generation atomically; pending generations live only in rotation preparation storage and are never served by current reads.

Identity role and member-role-set replicas are full-state and monotonic. Duplicate or out-of-order messages, including periodic anti-entropy replays, are ignored. Assignment reconciliation and policy replacement advance the same per-role optimistic fence, so a first-policy-create race cannot commit impact calculated before an invisible assignment; one side retries from the committed state. A changed role permission snapshot revalidates existing desired policies against the permission ceiling recorded at authorization time; a later elevation beyond that ceiling supersedes the prior operation and reconciles the desired selection fail-closed. System-role status alone never invalidates a policy. Role assignment/removal compares the union of all old and new role policies, so overlapping roles do not imply false removal. All provisioning and removal impact remains pending for a client-side cryptographic provisioner; the server never wraps VK.

`GET /api/vaults/{vaultId}/members` exposes only a keyset-paginated structural Member directory to an authorized current Member. Each row contains the opaque Member ID, a nullable display name from Vault's event-fed User replica, structural add timestamp, staged deprovisioning state and the selected Vault's active rotation ID when applicable. E-mail addresses, public keys and Vault/Entry presentation data remain outside this contract. Pages are ordered by Member ID, bounded to 100 and materialized without EF tracking.

## Staged Vault key rotation

`VaultKeyRotation` is the single active, tenant-first structural requirement for a Vault. Starting the planned flow is idempotent. An unlocked remaining Member claims a 120-second lease; every preparation batch and commit carries the current random fencing token, so an expired or superseded client cannot overwrite pending material or commit. Batches contain at most 100 server-validated encrypted items and are upserted by rotation, kind, subject, and subject version. Exact retries are no-ops; ciphertext replacement is allowed only while the current lease is valid. Stored payloads are opaque authenticated ciphertext, public manifests and recipient wrappers, never raw client keys.

Current Vault, Member, Entry, Discovery and Agent-manifest reads never join the pending table. Preparation therefore cannot expose a mixed generation. The backend stores the current VDK, Vault Agent Message private key and Vault Manifest Signing private key only as specialized authenticated ciphertext envelopes under VK. A claimant receives those three current envelopes plus its own current Member VK wrapper. After the claimant uploads the complete target recovery seed, a later authorized claimant can resume from that pending ciphertext under a fresh fence without persisting any raw client key. If the seed is incomplete, a new claim first persists its optimistic lease and then clears all prepared items through one statement fenced by that exact token and `LeaseRevision` before returning the token. The statement locks only the matching rotation row; a later claim either waits for this reset or makes the stale reset a no-op. A cleanup failure or superseded fence returns no token, so mixed target material is never accepted without a long explicit transaction.

Claimants read exact remaining-Member public keys and current Entry-key/Discovery source data through no-tracking keyset pages of at most 100 records. A separate page of at most 10 complete current `MemberIndex + MemberSecret` heads supplies the bounded source material needed to re-encrypt those projections during a Vault-key generation change. The database applies every cursor, ordering and limit; EF never tracks the complete Vault graph for pagination. Start, claim and preparation use the filtered active-rotation constraint plus `LeaseRevision` optimistic concurrency. Only finalization takes a per-Vault write lock. Under that short fence it checks the current Member-key directory, exact remaining Member and active organization-Agent recipient sets, every retained Entry-key wrapper, every current Member Entry head, every currently discoverable Entry projection, current manifest revisions, Vault metadata and the exact specialized Vault key envelopes required by the rotation scope. Prepared items carry their source structural revision. A racing mutation is detected through source revisions, `Vault.MutationVersion` or `LeaseRevision` and returned as a structural `409` reconciliation set. Member-head and Agent Discovery re-encryption preserve their current structural revisions while changing generation-bound ciphertext; Entry-key wrapper, Vault-key-material and Vault-metadata revisions advance exactly once.

Only a complete set can enter the atomic commit. A Vault-key rotation requires a target-generation replacement for each retained Entry-key wrapper and one complete target-generation `MemberIndex + MemberSecret` projection at the Entry's unchanged current revision and current key version. A batch that rotates the Agent Message or Manifest Signing family also carries the corresponding target public trust anchor. Each anchor is validated for the canonical scheme, key kind, target version, 32-byte key and computed fingerprint, and is fenced and stored as a prepared item beside its encrypted private-key envelope. Agent manifests, when recipients exist, must carry exactly the same target anchors. This allows a Vault with no active Agents to rotate both key pairs without relabeling old public keys or inventing a synthetic recipient manifest. One Vault transaction switches Member generation and all selected key heads, replaces the matching private envelopes and public trust anchors, replaces Member and Agent envelopes, re-wraps retained Entry keys, replaces complete current Member and Discovery ciphertext projections, invalidates pending reason envelopes encrypted to the retired Agent Message key, and marks the rotation committed. Incomplete material stays pending and current data remains fully usable. A committed retry is idempotent. The Entry generation fence then rejects future writes produced under the retired generation. There is no emergency-mode availability branch in this flow.

Member removal and Agent deactivation use a durable `VaultPrincipalDeprovisioning` coordinator. It processes affected Vaults deterministically and one at a time; each Vault commit is atomic and monotonic, but there is deliberately no distributed transaction across Vaults. Member removal widens the rotation to all key families and removes the Member envelopes and structural membership in that same commit. Agent deactivation rotates only the VDK-bound projection and removes the Agent's grant/discovery envelopes in that same commit. Finished Vaults never restore access, while unfinished Vaults remain usable. The target principal cannot claim or complete its own rotation, and every access-creating mutation is fenced against an active operation. Removing the last Member is persisted as blocked until an explicit ownership-transfer or deletion flow makes progress possible. Final completion delivery is idempotently recoverable by retrying either the committed rotation or the original deprovisioning request. Completion consumers reject stale timestamps before validating the active request, so delayed delivery cannot undo a later principal lifecycle transition.

## Agent Discovery provisioning

Agent Discovery is organization-wide: every active Agent in the Vault's Organization is a recipient candidate, independently of grants. `GET /api/vaults/{vaultId}/discovery/agents` returns that complete logical set through deterministic Agent-id keyset pages. `pageSize` defaults to 50 and is constrained to 1–100; `afterId` resumes strictly after the previous page and `nextAfterId` is present only when another page exists. Each item carries the human-readable Agent name, `current` or `pending` provisioning status and both public identity keys. Clients must follow `nextAfterId` to exhaustion and must not treat the first page as the complete set. Pagination never narrows Discovery to an authorization subset.

An authenticated structural Vault Member with `VaultManage` uploads one client-created `AgentVaultDiscoveryEnvelope` and its signed `VaultManifest` through `PUT /api/vaults/{vaultId}/discovery/agents/{agentId}`. The canonical `AgentVaultDiscoveryEnvelope` table is keyed by `(OrganizationId, VaultId, AgentId)` and stores only the opaque Agent-wrapped VDK, signature, public trust anchors, fingerprints, versions and provisioning metadata. It never stores raw VDK, VK, private keys or API-key credentials. There is no parallel discovery V2 entity/table/API.

The backend verifies the frozen canonical manifest bytes and Ed25519 signature, exact 32-byte X25519 and Ed25519 Agent identities/fingerprints, Vault signing/message trust anchors, wrapped-VDK digest, tenant scope, current key versions, canonical microsecond `issuedAt` precision and minimum runtime protocol. Values with finer timestamp precision fail before persistence so PostgreSQL cannot alter signed bytes. Enrollment enforces the same X25519 length, so an active Agent cannot become impossible reconciliation work. The first valid manifest pins the Vault trust anchors; later silent substitution fails closed outside the explicit rotation flow. An exact retry is idempotent, while a reused revision with different content or a backwards revision is rejected.

`GET /api/agent/vault-manifests` uses the existing Agent authentication scheme (organization API key plus Ed25519 request proof), requires `X-Palladin-Vault-Protocol: 2`, and returns the authenticated Agent's current access epoch plus only envelopes for that concrete active Agent whose recipient and Vault key versions are current. A valid Member-side provisioning commit makes the manifest available immediately; there is no second pairing activation or confirmation gate. The backend revalidates every stored envelope and signed manifest before release, and a failed binding or signature check returns a structural conflict without ciphertext. Agent deactivation first persists the canonical inactive replica and then revokes grants and tombstones discovery envelopes in bounded, retryable commits. Provisioning, grant creation and deactivation all advance `Agent.MutationVersion`; a stale writer receives an optimistic conflict instead of holding cross-aggregate locks. A later non-deactivated replica state supersedes an older deactivation; a later `Deactivated` replica does not skip the delayed cascade, so grants and envelopes are still revoked without rolling its timestamp backwards. The tombstone retains the highest accepted manifest revision: an exact retry stays revoked and reactivation requires a strictly higher signed revision. Hard Agent deletion removes the tombstone. This server-side revocation is not cryptographic erasure of a VDK already delivered to the Agent. Full cryptographic revocation requires rotating the VDK and reprovisioning every remaining authorized Agent.

## Snapshot and delta synchronization

Member clients synchronize encrypted Entry heads through `POST /api/vaults/{vaultId}/sync/snapshot` and `POST /api/vaults/{vaultId}/sync/delta`. An Agent uses the separate Discovery audience at `POST /api/agent/vaults/{vaultId}/discovery/sync/snapshot` and `POST /api/agent/vaults/{vaultId}/discovery/sync/delta`. Member endpoints require the existing JWT, `VaultManage`, verified email and structural Vault membership. Agent endpoints require the exact active Agent identity, current access epoch and a current non-revoked Vault Discovery envelope; they validate that envelope and its signed manifest before reading. Missing or cryptographically invalid authorization fails as the same `404` without ciphertext, so it does not reveal whether a foreign Vault exists or turn corrupt material into a server error. Snapshot and delta never retain a transaction or row lock while materializing or writing a response. Agent reads capture an authorization stamp and repeat the complete Agent/Vault/envelope validation immediately before send; any status, epoch, key or manifest change returns `409 sync-state-changed` without releasing the stale page.

Current Member Entry clients use the separate frozen policy-2 slices at `POST /api/vaults/{vaultId}/current-entries/sync/snapshot` and `POST /api/vaults/{vaultId}/current-entries/sync/delta`. Every `head` is one indivisible current `MemberIndex + MemberSecret + EntryKey` item; all three envelopes must bind the independently authoritative current Member-key generation, current Entry revision and current Entry-key version. Historical-generation ciphertext is never relabeled or accepted as current. The response also carries the exact current Member VK wrapper and an authenticated finite offline-access context. The context binds the authenticated principal and organization membership generation, structural Vault/Member, Member-key generation, VK version, current independently resolved Member recipient-key version/fingerprint, organization policy/version and `issuedAt/notAfter`. Identity is the authority for the membership generation and organization policy: it signs those values into the access token and validates them against current Identity state during JWT authentication. Vault consumes that authenticated request context without a live cross-module query, then independently resolves structural membership, current generations, recipient-key directory and the exact wrapper. Policy-2 cursors bind those generations and the stable sequence boundaries with a dedicated server-HMAC purpose. A security-generation or policy change rejects a stale access token; after token refresh, any cursor bound to the previous authority requires reset. Tamper, expiry or foreign-principal/Vault replay is an invalid cursor. These endpoints intentionally do not admit an organization membership in `Removing` state.

The finite organization policy is exactly `disabled`, `1h`, `4h` or `24h` (default and maximum `24h`). `disabled` produces `notAfter == issuedAt`; it does not silently mean unlimited access. Sync responses renew authority, while a per-Entry reveal/copy/TOTP/autofill operation does not. Policy-1 endpoints remain separate and secret-free for compatibility; there is no `includeSecrets` flag or mixed response shape. The policy-2 implementation and tests vendor the frozen `palladin-protocol` fixtures at commit `f0d1563cf04eb790b5b8e3b28f974a6301338100`.

The first snapshot page captures the audience-specific Vault sequence before reading heads. Snapshot pages use raw Entry UUID keyset order and a 15-minute HMAC-authenticated cursor bound to principal type and id, Organization, Vault, audience, protocol, base sequence, last Entry id and expiry. The client must close the snapshot with a delta strictly after that base. Duplicate projection revisions caused by concurrent writes are harmless and clients retain the highest typed projection revision.

Each Member `head` includes the structural `UpdatedAt`, the opaque `MemberIndex` and its current `VaultEntryKey` wrapper so the client can order locally synchronized Entries and unwrap the EntryDEK without a per-Entry detail request. Snapshot and delta join by the tenant-first Entry identity plus `CurrentKeyVersion`, materializing exactly one no-tracking key per head rather than the historical key collection. A missing current wrapper fails closed; a tombstone carries no timestamp or envelope. Agent Discovery responses never contain these Member-only fields.

Member sync is lock-free. A committed VK rotation advances `MemberSequence` once and sets the Member retention floor to that value, invalidating all pre-rotation incremental state and forcing a fresh snapshot instead of attempting to journal every in-place key rewrap. Snapshot completion through the bounded delta closes races without holding a database transaction through HTTP serialization.

The first delta page captures a stable upper bound. Continuations additionally bind sync policy, initial sequence, last safely scanned sequence and upper bound. Journal rows are scanned in sequence order and only `EntryId` plus the audience counter are materialized; current heads or structural tombstones are then resolved through the read context. For the Member audience, Active, Archived and the 30-day recoverable Deleted state remain encrypted heads; only a permanently purged, absent head becomes a tombstone. For Agent Discovery, every non-Active or non-discoverable Entry becomes a tombstone. Repeated changes coalesce to one current projection per affected Entry. Cursor advancement stops at the largest complete contiguous journal prefix that fits the requested scan count and the 2 MiB encoded JSON budget. Responses are capped at 200 items, carry `Content-Encoding: identity`, and never contain plaintext or keys.

Backend CI enforces deterministic structural performance gates for representative Vaults of 1,000, 10,000 and 20,000 Entries with a one-percent delta workload. The gate reports only Entry counts, page counts and maximum logical ciphertext bytes. It verifies the 100-item operational page, 200-item hard ceiling, 2 MiB encoded-response ceiling, 100-item rotation batch, 20-item history page and 100-version history ceiling. Initial sync contract inspection additionally prevents MemberSecret, Grant and History payloads from entering snapshot items. Wall-clock p95, CPU and resident-memory thresholds remain release artifacts measured on representative deployment hardware; CI does not invent unstable host-specific timing limits.

Member and Discovery counters and retention floors remain independent. `afterSequence` below its floor returns `409 resetRequired` with the current sequence and floor; timestamps never act as completeness cursors. Every sync request must provide `X-Palladin-Vault-Protocol: 2` and `X-Palladin-Sync-Policy: 1`; unsupported clients receive `426` before any ciphertext response. Cursor authentication uses a domain-separated HMAC key obtained through the shared server key-derivation boundary, so Vault never reads another module's configuration layout and no cursor secret or client key is persisted in Vault storage.

## Entry aggregate

`VaultEntry` is the only Entry runtime aggregate. Its tenant-first head key is `(OrganizationId, VaultId, Id)`. The head contains lifecycle state, current typed revisions, current Entry-key version, server-owned actor/timestamp metadata, the current encrypted `MemberIndex` projection and the optional current encrypted `AgentDiscovery` projection. It contains no label, description, icon, type, domain, field collection, generic content blob or mutable Member secret.

Entry key material and canonical content are separate records:

- `VaultEntryKey`, keyed by `(OrganizationId, VaultId, EntryId, KeyVersion)`, stores one authenticated EntryDEK wrapper plus its independent wrapper revision, Member-key generation and VK wrapping version;
- `VaultEntryVersion`, keyed by `(OrganizationId, VaultId, EntryId, Revision)`, stores one immutable full `MemberSecret` ciphertext snapshot and server-owned change metadata;
- each version has a composite FK to the exact Entry key version it used;
- unique `(OrganizationId, VaultId, MemberSequence)` and filtered unique `(OrganizationId, VaultId, DiscoverySequence)` indexes preserve the two synchronization orderings.

`CurrentRevision` resolves the current semantically immutable version; the Entry head never duplicates its `MemberSecretCiphertext`. Every ordinary mutation must replace `MemberIndex` at exactly the next `CurrentRevision`, so the complete current sync head always satisfies `MemberIndexRevision == CurrentRevision`. The only ciphertext-only exception is an atomic Vault-key generation rotation: it replaces the current version's authenticated `MemberSecret` bytes and current `MemberIndex` bytes at the same revision, key version, operation and server-owned history metadata, while retained non-current versions remain unchanged. `AgentDiscoveryRevision` remains a separate namespace and may lag after a Member-only update. A key switch, canonical secret version and every changed projection are validated and committed atomically. Stale `baseRevision`, scope substitution, skipped projection revisions, stale key generations and partial key switches fail closed. An idempotent retry never appends another key, version or sequence. It succeeds only when the complete submitted transition shape matches the immutable committed transition: key presence/content, Member Index content and Agent Discovery changed/disabled/content must all agree. `VaultEntryVersion.MemberIndexChanged`, the version key and its optional Discovery sequence retain only the structural facts needed for that comparison; no plaintext or duplicate projection is stored.

## Entry lifecycle, history, and irreversible purge

Every Archive, Delete, and Restore transition appends exactly one immutable canonical `MemberSecret` revision. Archive suspends delivery without revoking grants and removes the Entry from normal list, search, icon-upload, request, Discovery, and delivery paths. Restore appends a new head rather than rolling back history; an envelope for an older revision remains non-deliverable until an authenticated Member refreshes it against the restored revision. Delete removes all matching grant material and revokes an affected granular grant; restoring the Entry can never reactivate those deleted grants. A Deleted Entry is recoverable for exactly 30 days and remains visible only through the authenticated Recently Deleted surface during that window. Each Recently Deleted row includes the server-authoritative `RetentionExpiresAt`, so clients never duplicate the configured duration when presenting the deadline.

`GET /api/vaults/{vaultId}/entries/{entryId}` returns both the optional current Agent Discovery revision and its non-secret high watermark. The latter remains available while an Entry is Archived/Deleted so an unlocked Member can generate the exact next Discovery revision during restore instead of guessing from unrelated canonical revisions.

`GET /api/vaults/{vaultId}/entries/{entryId}/history` lazily returns encrypted versions in descending revision order with the exact encrypted Entry-key envelope referenced by each version, so a Member can decrypt history across Entry rekeys without receiving any raw key. The endpoint uses a default page size of 20, a maximum page size of 100, identity encoding, and the shared 2 MiB encoded-response ceiling. The server advertises the active retention policy. Automated compaction retains at most 100 versions and never retains a non-current version longer than 365 days; the current version is never removed. Explicit and scheduled compaction atomically advance the Member and Discovery retention floors so a client with an unsafe cursor receives `resetRequired` instead of an incomplete delta.

Permanent destroy, scheduled purge after 30 days, and startup replay use one fail-closed path. The first ordinary domain commit marks the Entry `IsPurging`, hides it from serving paths and persists the stable actor/time plus whether a ledger record is required. The service then appends the deterministic opaque record to the external S3 Object Lock bucket and purges object versions without an open database transaction. A final optimistic domain commit removes database content, wrapped keys, immutable versions and grant material. Failure leaves a hidden durable operation that the lifecycle job or exact request retry resumes idempotently. The record contains exactly `purgeKeyVersion`, a lowercase HMAC-SHA256 token, and `purgedAt`; it contains no tenant, Vault, Entry, user, ciphertext, or key identifier. The HMAC input is the ASCII domain `PLDN-PURGE-ENTRY-v1` followed by the canonical big-endian Organization, Vault, and Entry UUID bytes. Versioned HMAC keys are read only as SSM `SecureString` values, are cached in process memory, and are never logged or persisted by the application.

## Encrypted presentation assets

Vault and Entry icons use one private, immutable encrypted-asset contract. A client validates the image locally, encrypts it with resource-bound AAD, and uploads at most 5 MiB of ciphertext. The backend accepts only the declared `image/jpeg`, `image/png`, or `image/webp` presentation classes, verifies a canonical SHA-256 ciphertext digest, and writes the bytes as `application/octet-stream` with `private, no-store`. Object keys are generated server-side under `encrypted-assets/{opaqueStorageId}` and contain no Organization, Vault, Entry, domain, URL, filename, or display name. Metadata is keyed tenant-first by `(OrganizationId, VaultId, AssetId)` and an Entry asset has a composite FK to `(OrganizationId, VaultId, EntryId)`.

Upload, short-lived private download, and deletion all require verified Vault membership and `VaultManage`. Exact upload retries and races are idempotent through the tenant-first unique key; changing ciphertext under an existing asset id fails closed. Archive and Recently Deleted retain encrypted assets so local clients can render and restore them. Explicit deletion first commits `Deleting`, performs versioned object cleanup outside a transaction, then removes metadata; an interrupted deletion is hidden and safely retryable. Vault deletion uses the same durable pattern through `Vault.IsDeleting`. Permanent Entry purge, Vault deletion, and purge-ledger replay delete every object version. The zero-knowledge cutover removes the cached-domain table and blocks non-development startup until every legacy `favicons/`, `entry-icons/`, and `vault-icons/` object version and delete marker has been removed. The Vault module never accepts a domain, resolves a remote image, searches cached favicons, returns a public asset URL, or inspects plaintext image bytes. Optional public website branding is isolated in PublicAssetCatalog: clients call its authenticated ensure boundary only during create/edit/import, then encrypt the immutable `assetId`, `revision`, and delivery URL only when the catalog returns a `Ready` asset.

Production must provide `Modules__Vault__PurgeLedger__BucketName` for a versioned bucket created with Object Lock enabled, `Modules__Vault__PurgeLedger__KeyParameterPrefix` for the exact-scope SSM key path, and the workload IAM permissions needed only for `s3:PutObject`, `s3:GetObjectVersion`, and `s3:ListBucketVersions` on that bucket/prefix plus the retained SSM key versions. Ledger objects are Compliance locked for at least 120 days. Startup enumerates every object version and fails closed if it finds a delete marker, so a marker cannot hide a retained purge record during rollback replay. A retired HMAC key must remain readable for at least 120 days after its final use. Database and object backups/PITR must expire within 90 days. On every non-development startup, the service reads and validates all retained ledger payloads and locks, requires every referenced key version, recomputes opaque tokens for current Entry heads, and re-purges any Entry resurrected by restore. Missing configuration, inaccessible/invalid ledger data, unavailable keys, short retention, asset deletion failure, or ledger append failure prevents content deletion or application startup; none may be bypassed.

The destructive `ReplacePlaintextEntriesWithCanonicalEncryptedModel` migration drops the retired `Entries` table and creates only `VaultEntries`, `VaultEntryKeys`, `VaultEntryVersions` and bounded Entry creation challenges. Its rollback refuses to recreate the plaintext schema. There is no `Entry`/`EntryContent` legacy domain type and no alternate `*V2` graph.

The Agent Discovery cutover is also pre-production and intentionally destructive. It resets the Vault module's Agent replicas and dependent grant/failure-report rows before requiring valid Ed25519 public keys; it never manufactures placeholder keys, backfills another model, or introduces a compatibility path. Enrollment events rebuild the one canonical Agent replica. The migration is intentionally irreversible because deleted pre-production data cannot be reconstructed safely.

Revision-bound GRANULAR grants use two records. Durable `GrantEntryScope` stores only the exact Entry, fields, methods, expiry, and usage constraints; ephemeral `GrantEntryEnvelope` stores the filtered Agent ciphertext and is deleted on revoke, expiry, consumption, deletion, or supersession. Create and import never fan out credential ciphertext to existing grants. Update refreshes only active GRANULAR envelopes affected by the exact Entry revision and commits the Entry plus those refreshes atomically. Missing, stale, substituted, broadened, or duplicate GRANULAR envelope sets fail closed with `409`; exact Entry retries remain idempotent.

Each active FULL grant instead owns exactly one `AgentWrappedVaultKey`: the current 32-byte Vault key sealed client-side to that concrete Agent's authoritative X25519 key. Its canonical descriptor binds Organization, Vault, Grant, Agent, Agent access epoch, recipient key version and fingerprint, Vault-key version, suite and purpose. Package validation dispatches fail-closed by the explicit wrapper suite id; protocol 2 currently accepts only the frozen `palladin-x25519-sealed-box-v1` suite. Adding a suite requires a coordinated protocol contract for its context, key kinds, limits and all clients, not a silent fallback. The backend stores and returns only ciphertext. Credential delivery combines that wrapper with the requested Entry's current `VaultEntryKey` and `MemberSecret`; the native Agent runtime validates every binding, opens VK only in its native crypto boundary, derives the Entry key and exposes only method- and policy-authorized credential fields. No FULL-grant work is required when an Entry is created, imported or updated.

Each active `ScriptExecutionGrant` authorizes one parent Script through one complete Agent-encrypted execution package. The package contains the Script plus every referenced Entry at exact revisions, so the Agent obtains and executes the complete package in one request rather than requesting one grant per reference. The producer signature binds the package to the Vault manifest-signing key, Agent identity and access epoch, parent Script, ordered scope set and package revision; the backend validates these structural and signature bindings without decrypting the package. Proactive creation uses the separate `POST /api/vaults/{vaultId}/scripts/{scriptEntryId}/grants` endpoint. A FULL grant with `Exec` supersedes the same Agent's active direct Script grants atomically; FULL without `Exec` does not.

`GrantEntryScope.DeliveryPolicy` is an authenticated, explicit server-side discriminator for delivery safety: `Standard` permits the methods selected by the grant, while `ExecOnly` and `InjectOnly` can impose a narrower caller-selected policy. Entry type never derives this policy: Credential, API Key, Credit Card, Script, and custom Entries default to `Standard` and support any valid user-selected Grant method set. The backend persists and enforces an explicitly submitted policy before incrementing the use counter, but never stores or parses the encrypted Entry type or treats field identifiers as a type discriminator. A policy mismatch returns the existing policy-specific denial and consumes no grant use.

The GRANULAR grant envelope additionally persists the exact Member-key generation and recipient Agent-key version used by the frozen `grant-payload` AAD. Every mutation validates both values against the locked Vault and current Agent replica; a key rotation or stale recipient context therefore fails closed instead of storing undecryptable material. FULL creation is a single client-encrypted request containing one canonical `AgentWrappedVaultKey`, independent of Vault size. Vault-key rotation requires an exact replacement wrapper for every retained active FULL grant before atomic commit. Revocation, expiry, consumption, Agent deactivation and deletion remove the stored wrapper and immediately block online delivery; cryptographic revocation of a VK already opened by a compromised Agent requires rotating that Vault key.

The pre-production `AgentWrappedVaultKey` cutover deletes legacy FULL grants because their former per-Entry ciphertext cannot be converted into a truthful whole-VK wrapper without client key material. GRANULAR grants remain on their existing exact-entry model.

The pre-production frozen-AAD cutover deletes existing grants and their cascading scopes, encrypted reasons, and envelopes before making those two context columns mandatory. Earlier ciphertext cannot be assigned truthful values without client keys, so the migration is intentionally irreversible rather than backfilling placeholders or leaving undeliverable active grants.

`EncryptedReasonEnvelope` follows the frozen wire object exactly: `requestRevision`, the complete nested envelope header, member-key generation, and recipient Agent Message-key fingerprint are covered by the `PLDNV2SIG:ENCRYPTED-REASON:` signature. The backend rejects flattened legacy objects, stale/wrong recipient fingerprints, header duplication mismatches, and ciphertext over 4 KiB. The envelope remains attached to the Grant after approve, deny, revoke, expiry, or consumption so an authorized unlocked client can render the original access reason in Grant history; lifecycle transitions delete credential-delivery envelopes only. Deleting the Grant/Entry still cascades the reason, and pending reasons addressed to a retired Agent Message key remain invalidated. The contract-alignment migration discards only legacy encrypted-reason dependents because their missing authenticated fields cannot be truthfully reconstructed.

Grant management responses expose server-authoritative action capabilities. `CanRevoke` is true only for an active Grant. `CanGrantAgain` is true only for a terminal Grant whose Agent and target are still active and which has no effective active coverage. When coverage blocks re-granting, `ActiveCoveringGrantIds` contains the newer active Grant ids that cover the same current Entry revision (or the same Vault through an active FULL Grant). Inactive Agents never expose stale Grant rows as effective coverage. Clients use these identifiers to open the active Grant and offer its normal revoke flow; they do not infer coverage from status or client-side list contents.

## Creation protocol

The backend owns Vault identifiers while the client must bind ciphertext AAD to the final identifier:

1. `POST /api/vaults/creation-challenges` issues a random Vault id scoped to the authenticated Organization and Member, with a short TTL. A unique tenant/Member constraint bounds storage to one row; repeated or concurrent requests return the same active challenge.
2. The client encrypts `MemberVaultMetadata` and seals the creator's VK envelope using that scope.
3. Identity sends the Vault-owned idempotent `UpsertMemberKeyDirectoryCommand`, and Vault materializes the authenticated version plus frozen protocol-2 X25519 fingerprint in its local `MemberKeyDirectory`. Creation reads only this local projection; it never requests current Identity state, reads Identity persistence or injects an Identity query interface. If the command has not arrived, creation fails closed and the client retries after projection readiness. An exact setup retry republishes the command without replacing stored key material, providing a recovery path after an interrupted publication.
4. `POST /api/vaults` or `POST /api/account/default-vault` consumes the challenge exactly once and atomically persists the aggregate.

A missing, foreign, expired, or consumed challenge is rejected. Organization administrators cannot bypass structural Vault membership to retrieve encrypted projections or Member key envelopes.

Entry identifiers are also server-owned because every Entry envelope binds the final id in AAD. `POST /api/vaults/{vaultId}/entries/creation-challenges` reserves one id by default or a bounded batch of at most 500 for import. The authenticated Member encrypts the complete transition against those scopes. Create and import consume every reservation in the same transaction that stores the Entry heads, keys, versions and projections. An exact create retry is recognized from the already committed canonical transition before reservation consumption is checked.

Member key versions are the directory ordering authority. A higher version replaces an older fingerprint even when event timestamps are equal or arrive out of order; a lower version is ignored, and a different fingerprint for the same version fails closed. Timestamps remain diagnostic metadata and never substitute for the monotonic key version.

## Wire invariants

- Binary values are canonical unpadded base64url.
- Unsigned 64-bit revisions and sequences are canonical decimal strings in JSON.
- Metadata AAD binds protocol, suite, resource kind, projection kind, exact resource revision, key version, Member-key generation, Organization id, and Vault id.
- Entry AAD additionally binds Entry id and the concrete projection. `MemberSecret`, `MemberIndex`, `AgentDiscovery`, and wrapped Entry-key envelopes use their own typed revision/version namespaces; their numeric values are never treated as interchangeable counters.
- The server owns structural counters: creation binds revision, Member generation, and all initial key heads to `1`; an update must use exactly `current MetadataRevision + 1`. Stale, skipped, or exhausted revisions fail closed.
- XChaCha20-Poly1305 nonces are exactly 24 bytes; recipient-key fingerprints are exactly 32 bytes.
- Entry ciphertext bounds are 32 KiB for `MemberIndex`, 256 KiB for `MemberSecret`, 16 KiB for `AgentDiscovery`, and 64 bytes for the wrapped EntryDEK.
- The server validates structure, scope, bounds, revisions, and generations, but never decrypts ciphertext.
- A Vault manifest signature uses the frozen `PLDNV2SIG:VAULT-MANIFEST:` domain and JCS/RFC 8785 canonical unsigned manifest; Agent-wrapped VDK digests use `PLDNV2DG:AGENT-WRAPPED-VDK:`. Both bind the big-endian protocol discriminator `2`.

## Persistence and events

Feature mutations load tracked aggregates through `VaultDomainWriteContext`, call domain methods, and commit through `CommitAsync`. Queries use `VaultDomainReadContext`.

Every committed Member-visible Vault mutation also emits one coalesced `VaultSyncInvalidatedEvent` carrying only the Vault id, the committed Member sequence, the aggregate mutation version and the occurrence time. After commit, the Vault trigger resolves the current authorized Members from persistence and maps the hint to Notification's `BroadcastVaultSyncInvalidationCommand`; it never relies on an optionally loaded aggregate navigation or sends SignalR inline from a feature. Member removal and Vault deletion instead carry an explicit pre-removal recipient snapshot and emit a `removed` tombstone to those former Members. Vault deletion emits that tombstone with the durable `IsDeleting` transition, before retryable external object cleanup, rather than waiting for physical row removal. Clients treat the event as an at-least-once hint and fetch the canonical encrypted REST delta.

Vault lifecycle events contain identifiers, actors, structural classification, and timestamps only. Audit metadata never contains Vault display fields or ciphertext. The destructive cutover truncates legacy Audit rows and, before serving non-development traffic, deletes and verifies every current/noncurrent object version and delete marker under the `audit-exports/` prefix. A durable Audit cutover marker prevents that one-off purge from being mistaken for an ongoing compatibility path; startup fails closed when complete external deletion cannot be verified.

Vault and Entry Search publishers, consumers, endpoint registrations, and the Search contract dependency were removed. Vault/Entry matching is exclusively client-local after unlock.

## Existing downstream scope

The canonical Entry head/key/version model, snapshot/delta synchronization, lifecycle, history, rollback-resistant purge, encrypted reasons, split revision-bound grant scope/envelope lifecycle, staged key rotation, encrypted assets, and opaque Search/Audit cutover are active. Transitional grant event contracts keep plaintext Vault/Entry presentation slots empty until those contracts are replaced; no backend code may resolve or persist a Vault or Entry name.
